## WP1 上传与补传

设计依据：`docs/design.md` 5.1、5.5、11。这是剩余工作里最大、最关键的一块。

**目标**：分段写完后上传到服务器，校验成功后删除本地文件；断网期间积压的分段恢复后排队补传，不挤占操作区网络。

**接口**（内部接口，前缀 `/agent/v1`，消息模型放 `everrec_core/protocol.py`）：

| 接口 | 说明 |
| --- | --- |
| `POST /agent/v1/uploads` | 请求体：`code, filename, started_at, ended_at, size, sha256, integrity, channel(realtime/backfill)`。返回 `upload_id` 和服务器已收到的字节数 `received`（断点续传）；同一 `code+filename+sha256` 已完成则直接返回 `done: true` |
| `PUT /agent/v1/uploads/{id}?offset=N` | 请求体为原始字节，每片 ≤ 1 MB；`offset` 必须等于已收到字节数，否则 409 并返回正确的 `received` |
| `POST /agent/v1/uploads/{id}/complete` | 服务器校验大小和 SHA-256，移入正式目录并写 `recording` 表，返回 `recording_id`；校验失败返回 422，Agent 从头重传 |
| `POST /agent/v1/backfill-slot` | 申请补传名额。服务器同一时刻最多放行 N 台（默认 5）；拿到返回令牌和有效期，拿不到返回 429 + `Retry-After` |

**服务端**：
- 临时文件放 `<录像根>/_incoming/`，完成后按 `{位置编号}/{yyyy}/{MM}/{dd}/{位置编号}_{HHmmss}.ts` 归档（WP3 会改为存 MP4）。
- 录像根目录由环境变量 `EVERREC_RECORDINGS_DIR` 指定，默认 `./recordings`，正式部署 `/srv/everrec/recordings`。
- 新建 `recording` 表（字段见设计文档第 11 节）；**引入 Alembic**，把 `db.py` 里的 `create_all` 换成迁移，现有 `agent`、`event` 表做成第一个迁移。
- 上传请求体大小上限在接口里校验，不依赖 Nginx。

**Agent**：
- 新建上传后台线程（不得阻塞主循环）。分段归档后进入队列；本地索引 `segments.jsonl` 的 `status` 按 local → syncing → synced / failed 流转。
- 两条通道：刚归档的分段走实时通道（默认限速 1 Mbps，始终允许）；积压的走补传通道（先申请名额，默认限速 4 Mbps，从旧到新）。
- 限速用令牌桶，按字节计；分片 1 MB；中断后用服务器返回的 `received` 续传。
- 连接失败按指数退避加随机抖动（5 秒起，上限 5 分钟）。
- 校验成功后删除本地文件（设计 5.1）。纯本地运行（`server` 为空）时不启动上传线程。
- 心跳里的 `pending_sync` 用真实的待传数量；补传完成后 `offline_since` 清空的现有逻辑保持不变。

**验收**：
- 测试：正常上传、断点续传（中途断开后续传，不重复传已完成部分）、哈希不符被拒并重传、补传名额满时 429 排队、限速生效（传 2 MB 在 1 Mbps 下耗时 ≥ 约 15 秒，可用小数值参数加速测试）。
- 端到端：起服务端和 3 个 `camera.type: test` 的 Agent，停服务端 1 分钟再恢复，所有分段都到了服务器、本地已删除、服务器文件 SHA-256 与原始一致、录像时间上没有缺口。在 PR 里贴出这次验证的输出。
- Agent 主循环在服务端完全无响应（例如接口一直不返回）时仍按时归档、按时检查。

**主要改动**：`packages/agent/src/everrec_agent/uploader.py`（新）、`agent.py`、`index.py`、`core/protocol.py`、`packages/server/` 新增 `uploads.py`、`db.py`、Alembic 目录。

## WP2 服务端保留天数、滚动覆盖、加锁

设计依据：5.4。依赖 WP1。

- 设置项：保留天数（默认 90）、滚动覆盖开关（默认开）、磁盘阈值 85% / 95%。第一版只有全局一套（WP4 做界面，本包先用环境变量或设置表默认值）。
- 后台任务每小时一次：删除超过保留天数的分段（文件和 `recording` 行一起），已加锁的跳过；每次删除写日志。
- 关闭滚动覆盖时不删除；磁盘 ≥ 85% 产生"空间不足"事件；≥ 95% 时上传接口返回 507，Agent 当作暂时不可用处理（录像留本地，继续录）。
- 加锁接口：`POST /api/v1/recordings/{id}/lock`、`/unlock`（管理网站用，需登录，见 WP5）。
- **验收**：测试覆盖过期删除、加锁不删、开关关闭不删、95% 时拒收且 Agent 不中断录制。

## WP3 录像回放

设计依据：10（录像回放页）、12（分段 MP4 直接播放）。依赖 WP1。

- 浏览器不能直接播 TS。上传完成时服务端用 `ffmpeg -c copy -movflags +faststart` 转封装为 MP4（不重新编码），成功后删除 TS，`recording.path` 指向 MP4。失败时保留 TS 并标记，供修复。
- 接口：`GET /api/v1/recordings?code=&from=&to=`（按时间查分段）；`GET /api/v1/recordings/{id}/file`（必须支持 HTTP Range，Starlette 的 `FileResponse` 已支持，需写测试确认 206）；导出（多段合并下载，可第二步做）。
- 回放页照 `design/source/Playback.dc.html` 和 `design/screenshots/02-playback.png`：按位置编号和日期检索、播放器、24 小时时间轴（标出缺口和修复片段）、分段列表、加锁按钮。
- 查看和下载写入操作日志（表结构简单即可，WP5 的登录用户名写入）。
- 已知偏差：分段文件名的 `started_at` 是落盘时刻，比画面实际开始晚约 1 秒（10 帧时约 1 秒、5 帧时约 3 秒，是编码器先攒几帧再输出造成的，与分段长短无关）。时间轴/按时间检索时可按这个量微调，录像本身一帧不少。
- **验收**：用 WP1 端到端产生的录像，回放页能连续播放一个时间段、时间轴缺口位置正确；Range 请求返回 206。

## WP4 设置页与配置下发

设计依据：4.6、7（第一版：全局一套 + 个别电脑单独覆盖）、10（设置页）。依赖 WP1 的 Alembic。

- 服务端设置表：全局一套 + 按位置编号或编号前缀（如 `SUB-B-2F-*`）覆盖；带配置版本号。
- 下发：心跳回复 `HeartbeatReply.settings` 带合并后的最终配置和 `config_version`。可下发项：画质（`quality` / `resolution` / `fps`）、水印、本地配额、分段时长、上传限速、补传名额相关参数。**不可下发**：录像目录、服务器地址、开机自启（AGENTS.md 原则 5）。
- Agent：把收到的配置缓存到 `state/server_config.json`，离线时用缓存；在**下一个分段边界**重启 FFmpeg 应用新档位（允许约 1–2 秒间隙，在 PR 中写明实测间隙）。
- 位置选项：服务器维护州 / 区 / 楼栋 / 楼层的可选值；心跳回复带上，供桌面端设置页（WP8）做下拉；Agent 本地值不在选项里时，设备墙上标出，请管理员确认。
- **画质设置（Leo 已定的交互，必须照做）**：
  - 默认只显示一条"画质"滑条，5 个挡：省空间 / 偏省 / ★标准 / 偏清晰 / 清晰，推荐挡（标准，720P / 10 帧）上画推荐标记。
    挡位、标签、推荐挡全部从 `everrec_core.profiles.quality_table()` 取，前端不写死；服务端提供一个接口把它给前端。
  - "高级"折叠区里两条滑条：分辨率 `360P / 480P / ★720P / 1080P`，帧率 `5 / 8 / ★10 / 12 / 15`。只能停在挡位上，不能连续取值；
    填了高级项就覆盖画质挡，提供"恢复推荐"按钮。**码率不出现在任何界面上**。
  - 超出摄像头能力的分辨率挡置灰：Agent 心跳里的 `camera_resolutions` 给出摄像头支持的分辨率（目前只有 Windows 能探测，为空时不置灰）。
  - 滑条下方实时显示代价：每台每小时上限（`Encoding.mb_per_hour_max`）、全部电脑每天约多少 GB、按现有硬盘剩余空间和保留天数还能存几天；
    存不够保留天数时标红并在保存前确认。注明"按上限估算，实际通常更低"。
  - 只有登录的管理员能改（WP5）；每次修改写操作日志（谁、何时、从什么改成什么）。服务端只接受 `profiles` 里定义的取值，其他值一律拒绝。
- 设置页照 `design/source/Settings.dc.html`：画质、水印、保留天数与滚动覆盖开关（WP2 的设置）、本地空间、上传限速、推送地址（WP6）、单独设置的电脑、位置选项、客户端下载与更新（WP9 接入）、子公司中转节点（WP10 接入）。各项先做能用的，未实现的入口隐藏。
- **验收**：在设置页把某一台改成"偏省"，该 Agent 在下一分段边界生效，其他台不变；服务器离线时 Agent 沿用缓存配置；
  提交非法画质值被服务端拒绝；摄像头不支持的分辨率挡在界面上置灰。

## WP5 登录与凭据

设计依据：10、15。依赖 WP1 的 Alembic。

- 管理网站：一个管理员密码（哈希存储，argon2 或 bcrypt），会话 Cookie（HttpOnly、SameSite=Lax），登录页按设计稿风格；`/api/v1/*` 的读接口（GET）公开，便于现场直接看状态；写操作要登录。
- 只读 API 令牌：`EVERREC_API_TOKEN`，给其他系统查询用；只读，带它做写操作返回 403。读接口本来就公开，令牌留作将来收紧读接口时的凭据。
- Agent 凭据：首次心跳（或单独的注册接口）时服务器签发设备令牌，Agent 存到 `state/agent_token`；之后所有 `/agent/v1/*` 需带令牌；管理网站可在设备详情抽屉里吊销（被吊销的 Agent 照常本地录制，状态上报失败）。
- 操作日志表：登录、查看录像、下载、加锁、改设置。
- **验收**：未登录做写操作返回 401、只读令牌做写操作返回 403；吊销后该 Agent 心跳被拒且本地录像不受影响；令牌只以哈希保存。

## WP6 事件推送

设计依据：8.3–8.5。**只做通用 JSON，不做企业微信、钉钉**（见 AGENTS.md 第 2 节）。

- 一个推送地址（URL + 可选自定义请求头 + 签名密钥），第一版用环境变量或设置表（WP4 合并后放到设置页）。
- 4 类事件：`recording.stopped`（没在录像）、`device.lost`（失联）、`storage.low`（空间不足，**需要新增**：Agent 存储检查为 warn / fail 时由服务端状态变化产生）、`device.recovered`（恢复正常）。前三类已在 `server/status.py` 有雏形。
- 消息格式按设计 8.4；请求头 `X-Event-Id`、`X-Timestamp`、`X-Signature: sha256=<HMAC(时间戳 + "." + 消息体)>`。
- 发件箱：新建 `delivery` 表，后台任务投递；5 秒超时；重试间隔 1 分钟、5 分钟、30 分钟、之后每 2 小时；连续失败超过 24 小时暂停并在设备墙顶部提示。
- 大批同时失联（`mass_lost`）合并为一条"疑似服务器或网络故障"，不逐台推送。
- 测试推送接口：立即发一条测试消息，返回对方状态码和内容。
- **验收**：用本地起的假接收端测试签名可验证、重试和去重（同一 `eventId` 不重复入发件箱）、服务重启后未投递的消息继续投递、批量失联只推一条。

## WP7 缩略图

设计依据：6.2（每分钟一张）。

- 摄像头被 FFmpeg 独占，不能另开一个进程取图。在同一个 FFmpeg 里加第二路输出：`split` 出一路，`fps=1/60`、缩到宽 320，用 `-f image2 -update 1` 持续覆盖 `state/thumb.jpg`。改 `core/ffmpeg.py` 的 `build_record_command`，并保证录像那一路参数不变（现有测试必须仍然通过）。
- Agent 每分钟把最新缩略图发给服务器：`PUT /agent/v1/thumbnail`（小数据，不受补传排队影响）。
- 服务端只保留每台最新一张；`GET /api/v1/devices/{id}/snapshot`；设备墙卡片显示缩略图（加时间戳参数防缓存），失联的显示最后一张并标时间。
- **验收**：测试中 `testsrc` 录制时 `thumb.jpg` 按间隔更新（测试里可把间隔参数调小）；CPU 占用相比改动前无明显上升（在 PR 里给出前后对比）。需要 Leo 在 Windows 上确认摄像头场景下缩略图正常。

## WP8 桌面端（PySide6）

设计依据：4.1、4.6、4.7、9.6、10。界面照 `design/source/Client.dc.html`、`Tray.dc.html`、`RepairTool.dc.html` 和对应截图。
新建包 `packages/desktop`（`everrec-desktop`），一个入口 `everrec-desktop`：默认客户端 + 系统托盘，`--repair` 打开修复工具，`--tray` 只常驻托盘（开机自启）。

**Agent 与界面之间的约定**（本包负责在 Agent 侧实现）：
- Agent 每轮把状态原子写入 `state/status.json`（先写临时文件再改名），内容为当前 `Heartbeat` 模型的 JSON 加 `online` 字段。界面只读这个文件和日志目录，不直接控制录制。
- 改设置：界面**直接写配置文件**，不弹 UAC（2026-10 Leo 定，见 AGENTS.md 第 2 节）；安装脚本把配置文件设成登录用户可改。
  Agent 检测到配置文件变化，在下一分段边界生效。`everrec-agent set-config` 仍保留，给命令行和安装包静默参数用。

**修复工具**（先做，最独立）：
- 拖入文件或文件夹 → 「检查并修复」→ 结果列表，文字用 `repair.FRIENDLY_TEXT`。
- 结果存到原文件旁的"已修复"文件夹（`repair_file(src, src.parent / "已修复")`），原文件不动；完成后"打开文件夹"按钮。
- 修复在后台线程，有进度条、可取消；折叠的"高级"区域显示日志。不需要服务器。

**托盘**：只显示状态（是否在录像、位置编号、连续录制时长、服务器连接），**不提供停止录制**。所有登录用户可见（开机启动项放在所有用户的启动目录，由 WP9 安装）。

**客户端窗口**：主界面（录制横幅、本机画面用 WP7 的 `thumb.jpg`、三项检查、今天的录像时间轴读 `segments.jsonl`、日志按级别查看、导出诊断包、保存当前屏幕）；左上角图标进入设置（位置、服务器地址、档位、录像文件夹、开机自启、定时截屏、打开配置文件、版本）。连上服务器时位置只能从服务器选项里选（WP4），未连上时自由填写。

**验收**：修复工具对正常 / 可修复 / 无法修复三类文件给出正确文字（可复用 core 的测试素材）；界面逻辑与 Qt 解耦的部分写单元测试（例如读 `status.json`、组时间轴数据）；PR 附三个窗口的截图（Linux 下 `QT_QPA_PLATFORM=offscreen` 可截图），并写 Windows 验证步骤。

## WP9 打包、安装与更新

设计依据：12、14.1、14.5。依赖 WP8。

- PyInstaller `onedir` 打包 Agent、客户端、托盘、修复工具；FFmpeg 放在程序目录的 `bin/`（`core/ffmpeg.py` 的 `ffmpeg_binary()` 已按这个位置查找）。在 README 注明 libx264 的 GPL 许可。
- 安装包（Inno Setup 或 NSIS 二选一，在 PR 里说明理由）：默认装到 `D:\EverRec`，没有 D 盘装 `C:\EverRec` 并把本地配额调小；卸载和升级保留 `recordings`、`config`、`logs`。支持静默安装参数（服务器地址、位置编号）。
- 安装时：用 `deploy/windows/everrec-agent-service.xml`（WinSW）注册服务；PowerShell 脚本开启"允许桌面应用访问相机"、电源计划从不睡眠、关闭 USB 选择性暂停；配置文件权限登录用户可改（见 AGENTS.md 第 2 节）；托盘加入所有用户启动项。
- 自动更新：管理员在网站上传新版本；Agent 每天在 02:00–04:00 检查并静默安装，失败回到旧版；可设为"只提醒"。
  **只在没人用桌面时装**：安装器要替换托盘和录屏进程的 exe，而它们在登录会话里被占用。
  没人用桌面 = 没有登录会话，或者登录着但**都锁屏超过 10 分钟**（心跳带 `desktop_idle`，
  由 `agent/sessions.py` 查 WTS 会话的锁屏标志得出；查不到按"有人在用"处理）。
  装之前 Agent 先结束登录会话里的 `everrec-screen`、`everrec-desktop`（退不掉就放弃本次更新，下一小时再试），
  摄像头录制在服务里、不受影响；这两个程序下次登录由启动项拉起（托盘图标会暂时消失，属正常）。
  录屏模式的机器例外：录屏进程必须常驻登录会话、锁屏时装完不会自己回来，所以仍然只在没人登录时更新。
  服务端返回 `waiting_for_idle` 时 Agent 只记日志、不下载。
  老版本 Agent 心跳里没有 `desktop_idle`，服务端按"有人在用"处理，所以现场机器要先手动装一次才能自动更新。
- **验收**：GitHub Actions（`windows-latest`）能产出安装包；Leo 在一台干净的 Windows 上完成安装 → 重启电脑后自动开始录制 → 卸载后录像仍在。验证步骤写在 PR 里。

## WP10 子公司中转节点

设计依据：3.1。依赖 WP1–WP5。

- 新包 `packages/relay`（`everrec-relay`），尽量复用服务端代码：对子公司 Agent 提供与服务器相同的 `/agent/v1/*` 接口，录像存在中转节点本地并按保留天数滚动覆盖，自己判定子公司设备失联。
- 对主服务器提供 `/relay/v1/pull`：设备状态、新事件、新增录像索引、缩略图，并接收配置变更；用独立密钥 + HTTPS，不依赖域账号。
- 主服务器每 30 秒拉一次；连续 3 次拉不到告警"子公司中转节点失联"，不逐台报失联。回放子公司录像时主服务器向中转节点按需取分段并短期缓存。
- **验收**：本机起主服务器、中转节点和两个 Agent（一个连主服务器、一个连中转节点），设备墙上两台都可见；断开中转节点时只出一条告警；能回放子公司那台的录像。

## WP12 屏幕录制源（与摄像头二选一）+ `source` 字段

设计依据：4.2 的"屏幕源的限制"、4.3。依赖 WP8（客户端进程）、WP9（启动项与打包）。
Leo 已定：录屏与摄像头**二选一**，同一个数据模型里把 `source` 维度留好，第一版界面不按源筛选。

**已经做完的（不用重做）**：
- 一键截屏：客户端主界面"保存当前屏幕"，`QScreen` 抓屏 + 时间水印，存 `screenshots/`。
- 定时截屏：`screenshot` 段（`enabled` / `interval_seconds` / `keep_files`）是本地设置，服务器不下发；
  由客户端进程的 `TimedScreenshots` 按间隔存图、超 `keep_files` 删最旧的。这是"本地保存"，不上传。
- 录屏参数与数据模型：`CameraType.SCREEN`；`ffmpeg._input_args` 的 gdigrab 分支；屏幕源默认 1080P / 8 帧、
  码率系数 0.10（`profiles.SCREEN_*`）；`recording.source` 列（0011 迁移）+ `UploadRequest.source`
  （默认 `camera`，旧版 Agent 兼容），服务端落库并随接口返回。
- 会话进程 `everrec-screen`（`agent/screen.py`）：跑在登录用户会话里，锁屏停 FFmpeg、解锁恢复，
  写 `state/screen.json`；独立单实例锁（`EverRecScreen`），多用户同时登录时只让第一个会话录。
  常驻不退出：配置里切成摄像头就待着不动，切回录屏不用重新登录（每轮重读配置）。
  打包入口 `packaging/windows/entry/screen.py`，安装包写进 HKLM Run（所有用户登录启动）。
- Agent 屏幕模式：不启动自己的 FFmpeg，改为读 `state/screen.json` 监督会话进程；锁屏时数据流检查不判失败、
  不去重启，心跳带 `paused="锁屏暂停"`；服务端在这种情况下判 `ok` 且不推送事件；设备墙/抽屉显示"锁屏暂停"。
- 客户端设置："连接与录像"卡片里加"录制画面"（摄像头 / 屏幕），写 `camera.type`；界面注明锁屏期间没画面。

**还没做的**：
- **验收**：Linux 上用 `testsrc` 走同一代码路径；Windows 上要 Leo 逐条验证（锁屏、切换用户、改分辨率、多显示器、
  杀进程后自动重启），PR 里写清"需要 Leo 在 Windows 上验证"，不得声称已验证。

## WP13 六级组织树与责任人

设计依据：[`org-tree-plan.md`](org-tree-plan.md)（Leo 的追加需求，不在设计文档里）。**已完成**，本节留作记录和后续扩展依据。

- 位置由"州 / 区 / 楼栋 / 楼层 / 编号"改为"部门 - 科室 - 区域 - 属地 - 位置 - 编号"六级；层级做成可维护的树，
  编号不进树（设备本身是叶子）。旧的四段配置仍可读，自动映射到新层级。
- 设备心跳带六级位置，服务端按它自动补齐缺的节点，设备归到最深的非空节点；对不上任何节点的归"未归位"。
- 责任人（姓名 / 部门 / 备注）可配在任意一级，下级没配就继承最近的上级；只用于显示。
- 接口：`GET /api/v1/org`（整棵树 + 每个节点含下级的设备汇总）、`POST/PUT/DELETE /api/v1/org/nodes`；
  心跳回复带 `location_tree`，桌面端设置里逐级联动选择。
- 表：`org_node`（0009 迁移）；停用的 `location_option` 由 0010 迁移删除。
- 网站：首页（原看板）左侧组织树、设备详情抽屉、设置页"组织与责任人"。首页只放编号和状态，**不放画面预览**（画面在设备墙看，避免两页重复）。
- **约束**：已经有设备的节点不能改 code（code 进文件路径，改了会割裂历史录像），只能改名称和责任人。
- **验收**（`test_org.py`）：心跳自动建树、状态向上汇总、责任人继承、旧版 Agent 归"未归位"、
  有设备的节点拒绝改 code 和删除。
